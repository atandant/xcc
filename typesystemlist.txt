xcc 0.0.1.3 Type System Bucket List
===================================

Purpose
-------

This file is the working bucket list for xcc 0.0.1.3.

The release goal is not "add every type feature."

The release goal is:

    Build the first real type system.
    Make basic pointers usable.
    Keep the scope small enough that the compiler stays understandable.

xcc remains a C89-targeting compiler.

We are allowed to temporarily deviate from C89 only when the deviation is:

    1. explicit,
    2. documented,
    3. tested when observable,
    4. tied to a reason,
    5. not hidden behind vague "C-like" language.

Important policy:

    xcc does not have a warning system yet.

Therefore 0.0.1.3 must not emit "warning:" diagnostics.

If a known deviation must be reported to the user, report it as a note or an
error depending on the situation.

For now, most deviations should be documented here and in focused comments.


Final Scope Decision
--------------------

0.0.1.3 includes:

    - a real Type representation,
    - builtin semantic types:
        void,
        char,
        int,
        pointer to T,
    - Type attached to declarations,
    - Type attached to parameters,
    - Type attached to functions,
    - Type attached to expressions,
    - basic pointer declarations,
    - address-of on lvalues,
    - dereference of pointer expressions,
    - assignment through dereferenced pointers,
    - pointer equality and inequality,
    - pointer truthiness in conditions,
    - void pointer compatibility,
    - temporarily retained implicit function declarations.

0.0.1.3 does not include:

    - char-correct byte codegen,
    - arrays,
    - pointer arithmetic,
    - sizeof,
    - casts,
    - structs,
    - unions,
    - enums,
    - unsigned types,
    - long,
    - short,
    - const,
    - volatile,
    - typedef,
    - old-style K&R function definitions,
    - complete C89 declaration grammar,
    - a warning system,
    - full integer promotions,
    - full usual arithmetic conversions.


Current Compiler Shape
----------------------

The current compiler has a clean small pipeline:

    lexer -> parser -> AST -> sema -> codegen

The parser mostly builds AST nodes.

sema currently owns:

    - local name resolution,
    - block scopes,
    - function declaration merging,
    - function redefinition checks,
    - function arity checks,
    - return value checks for void functions,
    - stack frame sizing.

codegen currently assumes:

    - values live in 64-bit registers,
    - local slots are 8 bytes,
    - expressions generally produce a value in %rax,
    - only variables are assignable lvalues,
    - assignment takes the address of a variable,
    - all arithmetic is integer-like.

0.0.1.3 must change the semantic truth without turning the compiler into a
large framework.


Core Design Principle
---------------------

Type information belongs in sema.

The parser should parse type syntax and attach parsed type objects to AST
declarations.

The parser should not decide whether expressions are type-correct.

The code generator should not infer language rules.

The code generator should ask already-typed nodes what they are and emit the
correct load, store, address, or comparison.

The type system should be small, recursive, and easy to extend.


Proposed Type Model
-------------------

Create:

    src/type.h
    src/type.c

Minimum TypeKind:

    TY_VOID
    TY_CHAR
    TY_INT
    TY_PTR
    TY_FUNC

Useful Type fields:

    kind
    size
    align
    base
    ret
    params
    nparams
    prototyped

Meaning:

    TY_VOID:
        no object size,
        legal function return type,
        legal base of pointer as void *,
        illegal variable object type.

    TY_CHAR:
        modeled semantic type only in 0.0.1.3,
        not advertised as byte-correct runtime storage,
        may be parsed and used in declarations/signatures.

    TY_INT:
        current main arithmetic type.

    TY_PTR:
        pointer to another type,
        pointer size is 8 on x86-64 SysV,
        pointer alignment is 8.

    TY_FUNC:
        function type,
        contains return type,
        contains parameter types,
        contains prototyped flag.

Required helpers:

    Type *type_void(void);
    Type *type_char(void);
    Type *type_int(void);
    Type *type_ptr(Type *base);
    Type *type_func(Type *ret, Type **params, int nparams, int prototyped);

    int type_is_void(Type *ty);
    int type_is_integer(Type *ty);
    int type_is_pointer(Type *ty);
    int type_is_scalar(Type *ty);
    int type_is_object(Type *ty);
    int type_same(Type *a, Type *b);
    int type_compatible(Type *dst, Type *src);
    int type_assignable(Type *dst, Type *src);

Possible helpers:

    int type_size(Type *ty);
    int type_align(Type *ty);
    const char *type_name(Type *ty);

Avoid:

    - string-based type comparisons,
    - integer flags like ret_void as the long-term function type model,
    - separate ad hoc pointer flags on AST nodes,
    - putting C compatibility logic in codegen.


AST Changes
-----------

Node should gain:

    Type *ty;
    int is_lvalue;

or:

    Type *ty;
    ValueKind value_kind;

Minimum acceptable version:

    Type *ty;
    int is_lvalue;

ValueKind is cleaner later, but int is enough for this stage.

NodeKind additions:

    ND_ADDR      for unary &
    ND_DEREF     for unary *

Existing ND_NEG remains unary arithmetic minus.

ND_ASSIGN currently says lhs must be VAR.

That comment must change.

New rule:

    lhs must be a modifiable lvalue.

For 0.0.1.3, assignable lvalues are:

    - local variables with non-void object type,
    - dereferenced pointer expressions whose base type is non-void.

Maybe later:

    - array elements,
    - struct members,
    - union members.

Param should gain:

    Type *ty;

Function should gain:

    Type *ret_ty;
    Type *ty;

Eventually ret_void can disappear.

In 0.0.1.3, ret_void may remain temporarily if migration is easier, but it
must become derived state, not the source of truth.


Parser Scope
------------

The parser must parse declaration specifiers and pointer declarators.

Minimum grammar support:

    int x;
    char c;
    void f(void);
    int *p;
    char *s;
    void *vp;
    int **pp;
    int *f(void);
    void f(int *p);
    int f(char *s, void *p);

Out of scope grammar:

    int (*fp)(void);
    int a[3];
    int *a[3];
    int (*a)[3];
    struct S s;
    typedef int T;
    const int x;
    unsigned int x;

For now, pointer syntax can be simple:

    type_spec pointer_opt IDENT

where:

    type_spec:
        int
        char
        void

    pointer_opt:
        empty
        pointer_opt '*'

This is not the full C declarator grammar.

This is a known subset.

It should be documented as an unsupported C89 feature, not silently presented
as full declarator support.


Declaration Rules
-----------------

Allowed object declarations:

    int x;
    char c;
    int *p;
    char *s;
    void *vp;
    int **pp;

Rejected object declarations:

    void x;

Reason:

    void is not an object type.

Allowed function returns:

    int f(void);
    char f(void);
    void f(void);
    int *f(void);
    void *f(void);

Function parameters:

    int f(int x);
    int f(char c);
    int f(int *p);
    int f(void *p);

Parameter special case:

    f(void)

means no parameters.

Not a parameter named nothing of type void.

Unnamed prototype parameters remain allowed where already supported:

    int f(int);
    int f(int *);


Expression Typing Rules
-----------------------

NUM:

    type is int.
    not an lvalue.

VAR:

    type comes from local symbol.
    is an lvalue if it names an object.

CALL:

    callee must not be shadowed by a local object.
    type is function return type.
    not an lvalue.

    Existing C89 implicit declaration behavior remains temporarily:

        unknown_call()

    creates an implicit function declaration equivalent to:

        int unknown_call();

    This is retained temporarily.

    It should be tracked as a legacy C89 area because it interacts poorly with
    stronger function types.

ASSIGN:

    lhs must be a modifiable lvalue.
    rhs must be assignment-compatible with lhs type.
    result type is lhs type.
    result is not an lvalue.

ADDR:

    operand must be an lvalue.
    result type is pointer to operand type.
    result is not an lvalue.

DEREF:

    operand must have pointer type.
    if operand type is pointer to void, dereference is invalid.
    result type is base type.
    result is an lvalue.

NEG:

    operand must be integer.
    result type is operand type for now.
    result is not an lvalue.

BINOP arithmetic:

    + - * / %

    0.0.1.3 supports integer operands only.

    Pointer arithmetic is out of scope.

BINOP comparison:

    == !=

    Supported for:

        integer vs integer,
        compatible pointer vs compatible pointer,
        object pointer vs void pointer,
        void pointer vs object pointer.

    Result type is int.

    < <= > >=

    Supported for integers only in 0.0.1.3.

    Pointer ordering is out of scope.

Conditions:

    if (expr)
    while (expr)
    for (; expr; )

    expr must be scalar.

    scalar means integer or pointer.

    void expression is invalid as a condition.

RETURN:

    return;

        valid in void functions.
        temporarily preserve existing behavior for int functions if desired,
        but note C89 semantics are not fully enforced there.

    return expr;

        invalid in void functions.
        expr must be assignment-compatible with function return type.


Void Pointer Compatibility
--------------------------

Decision:

    yes, support void * compatibility.

Minimum rules:

    T * can assign to void *.
    void * can assign to T *.
    T * can compare == != with void *.
    void * can compare == != with T *.

Where T is an object type.

Do not allow:

    dereference of void *,
    pointer arithmetic on void *,
    sizeof(void),
    variable of type void.

Example supported:

    int main(void) {
        int x;
        int *p;
        void *v;
        p = &x;
        v = p;
        p = v;
        *p = 3;
        return x;
    }


Char Scope
----------

Decision:

    char is part of the type model.

Decision:

    char-correct runtime behavior is not part of 0.0.1.3.

Reason:

    The release goal is the type system and basic pointer semantics.
    Byte-accurate storage and loads are a separate backend correctness step.

Allowed:

    char c;
    char *p;
    char f(char c);

But tests should avoid relying on byte truncation or byte-addressed char
object behavior unless that behavior is actually implemented.

If the compiler accepts char but still stores it in 8-byte slots, that must be
documented as a known temporary backend limitation.

Do not emit a warning.

Do not claim char codegen is complete.

If a user hits a case that would silently produce wrong code, prefer either:

    - reject that specific construct for now, or
    - emit a note explaining the known limitation.

Because there is no warning system yet, do not print "warning:".


Deviation Policy
----------------

xcc targets C89.

Known deviations are allowed only when explicit.

For 0.0.1.3, deviation tracking can be simple.

Possible internal API:

    typedef enum {
        XCC_NOTE_DEVIATION,
        XCC_NOTE_LIMITATION
    } NoteKind;

    void diag_note_at(SourceLoc loc, const char *fmt, ...);

But do not overbuild this yet.

No warning system in 0.0.1.3.

No "warning:" output in 0.0.1.3.

Possible user-facing output:

    file.c:3:5: error: dereference of void pointer
    file.c:3:5: note: xcc 0.0.1.3 supports void * conversions but not void * dereference

The note is supplementary.

It does not count as a warning.

Implemented (Stage 12):

    - diag_note_at(SourceLoc, fmt, ...) in src/diag.c
    - notes use the "note:" prefix, never "warning:"
    - notes do not increment diag_error_count
    - notes are suppressed unless at least one error was already reported
    - void pointer dereference emits the note above after its error

Known temporary deviations or unsupported C89 areas:

    - no old-style K&R function definitions,
    - implicit function declarations retained temporarily,
    - no implicit int,
    - no full declarator grammar,
    - no arrays,
    - no structs or unions,
    - no enum,
    - no typedef,
    - no full integer promotions,
    - no full usual arithmetic conversions,
    - char is modeled but not necessarily byte-correct,
    - int lowering may still use 64-bit operations internally.

Important distinction:

    Unsupported feature:
        xcc rejects valid C89 because the feature is not implemented.

    Temporary semantic deviation:
        xcc accepts code but may behave differently than C89.

    Internal implementation detail:
        xcc behaves correctly enough for current observable tests, even if the
        internal representation differs from abstract C semantics.

Only the second category is dangerous.

The second category needs the most care.


Stage 0: Baseline and Guardrails
--------------------------------

Goal:

    Confirm the existing compiler behavior before changing types.

Tasks:

    - run existing test suite,
    - note any failing tests before work begins,
    - do not update README status unless separately requested,
    - keep README user edits intact,
    - avoid unrelated refactors.

Verification:

    make test

Expected:

    all existing tests pass before type changes.

Tests added:

    none.

Exit criteria:

    We know the baseline.

------------------------

Goal:

    Add the semantic Type representation without changing user-facing
    behavior.

Tasks:

    - add src/type.h,
    - add src/type.c,
    - add TypeKind,
    - add builtin singleton types,
    - add pointer type constructor,
    - add function type constructor,
    - add type predicates,
    - add compatibility helpers,
    - add type names for diagnostics,
    - update Makefile sources.

Rules:

    Type allocation should use the existing arena if that fits local style.

    Builtin types can be static singletons.

    Pointer/function types can be arena allocated.

    Do not add a separate type interning system unless needed.

Verification:

    make
    make test

Expected:

    no behavior changes.

Tests added:

    none required.

Exit criteria:

    Type module exists and old tests still pass.


Stage 2: Thread Types Through AST Declarations
----------------------------------------------

Goal:

    Make declarations carry Type *.

Tasks:

    - add Type *ty to Node,
    - add Type *ty to Param,
    - add Type *ret_ty to Function,
    - add Type *ty to Function for full function type,
    - update node_decl constructor to accept Type *,
    - update param_append or replacement API to accept Type *,
    - update func_new to accept return Type *,
    - keep ret_void temporarily only if needed,
    - derive ret_void from ret_ty if retained.

Parser changes:

    - ret_type should return Type *,
    - params should create typed parameters,
    - local declarations should create typed declarations.

At the end of this stage, only int and void syntax need to behave as before.

char and pointer syntax can wait until Stage 3.

Verification:

    make
    make test

    existing behavior preserved.

Tests added:

    none required unless regressions appear.

    AST declarations have real Type *.

Stage 4: Symbol Tables Store Types
----------------------------------

Goal:

    Locals and functions resolve to typed symbols.

Tasks:

    - Local symbol stores Type *ty,
    - FuncSym stores Type *ty,
    - lookup local returns offset and type,
    - function registration compares function types,
    - conflicting return type errors use Type comparison,
    - conflicting parameter count errors remain,
    - eventually compare parameter types for prototypes.

Behavior:

    int f(int);
    int f(int *);

should conflict.

Behavior:

    int f(int *);
    int f(void *);

should conflict as function prototypes.

Reason:

    void * assignment compatibility does not mean function parameter types are
    the same type.

Required tests:

Stage 6: Lvalue Model
---------------------

Goal:

    Replace "lhs must be ND_VAR" with a real lvalue check.

Tasks:

    - add node lvalue tracking,
    - mark VAR as lvalue when it names an object,
    - mark DEREF as lvalue later,
    - mark NUM/CALL/BINOP/ADDR/ASSIGN as not lvalue,
    - assignment checks lvalue,
    - address-of checks lvalue.

Before ND_DEREF exists, only VAR is lvalue.

Required tests:

    error_addr_non_lvalue.c after address-of exists.

Verification:

    make test

    lvalue rules are centralized in sema.


Stage 7: Address-Of Operator
----------------------------

Goal:

    Implement unary & for lvalues.

Parser:

    expr:
        '&' expr

AST:

    ND_ADDR

Sema:

    operand must be lvalue,
    result type is pointer_to(operand->ty),
    result is not lvalue.

Codegen:

    generate address of operand.

For 0.0.1.3, addressable operands:

    - local variable,
    - dereferenced pointer after Stage 8.

Required tests:

    addr_local_int.c
    addr_local_pointer_typecheck.c
    error_addr_non_lvalue.c

Example:

    int main(void) {
        int x;
        int *p;
        p = &x;
        return 0;
    }

Verification:

    make test

Exit criteria:

    Taking the address of a local works and is type checked.


Stage 8: Dereference Operator
-----------------------------

Goal:

    Implement unary * for pointer values.

Parser:

    expr:
        '*' expr

AST:

    ND_DEREF

Sema:

    operand must be pointer type,
    pointer to void is invalid to dereference,
    result type is pointer base type,
    result is lvalue.

Codegen:

    as rvalue:
        evaluate pointer expression to address,
        load from address according to result type.

    as lvalue address:
        evaluate pointer expression to address,
        leave address in %rax.

Required tests:

    deref_int_pointer_read.c
    deref_int_pointer_write.c
    error_deref_int.c
    error_deref_void_pointer.c

Example:

    int main(void) {
        int x;
        int *p;
        p = &x;
        *p = 7;
        return x;
    }

Verification:

    make test

Exit criteria:

    Basic pointers are usable.


Stage 9: Typed Load and Store
-----------------------------

Goal:

    Stop treating all loads/stores as one undifferentiated operation.

Minimum 0.0.1.3 behavior:

    int:
        existing 64-bit lowering may remain temporarily if tests do not rely
        on exact C int width.

    pointer:
        8-byte load/store.

    char:
        semantic type exists, but byte-correct behavior is not required unless
        explicitly implemented.

Implementation:

    add:

        emit_load(Type *ty)
        emit_store(Type *ty)

or equivalent helpers.

Do not spread type-size decisions across codegen.

Required tests:

    pointer_store_roundtrip.c
    pointer_return_roundtrip.c
    pointer_arg_roundtrip.c

Optional tests if char runtime is rejected:

    error_char_runtime_unsupported.c

Optional tests if char runtime is allowed but word-backed:

    char_decl_parse_only.c

Verification:

    make test

Exit criteria:

    Pointer read/write codegen is not mixed with integer-only assumptions.


Stage 10: Pointer Equality and Truthiness
-----------------------------------------

Goal:

    Support the agreed pointer expression behavior.

Equality:

    p == q
    p != q

Allowed:

    same pointer type,
    object pointer with void *,
    void * with object pointer.

Rejected:

    pointer == int,
    pointer != int.

Ordering:

    p < q
    p <= q
    p > q
    p >= q

Out of scope for 0.0.1.3.

Conditions:

    if (p)
    while (p)
    for (; p; )

Allowed because pointer is scalar.

Required tests:

    pointer_eq_same_type.c
    pointer_ne_same_type.c
    pointer_eq_void_ptr.c
    pointer_condition_if.c
    pointer_condition_while.c
    error_pointer_ordering.c
    error_pointer_eq_int.c

Verification:

    make test

Exit criteria:

    Pointers work in equality and control-flow conditions.

Stage 14: Final Acceptance Tests
--------------------------------

Goal:

    Prove 0.0.1.3 scope is met.

Must-pass example:

    int main(void) {
        int x;
        int *p;
        p = &x;
        *p = 42;
        return x;
    }

Must-pass void pointer example:

    int main(void) {
        int x;
        int *p;
        void *v;
        p = &x;
        v = p;
        p = v;
        *p = 9;
        return x;
    }

Must-pass pointer parameter example:

    void set(int *p) {
        *p = 5;
    }

    int main(void) {
        int x;
        set(&x);
        return x;
    }

Must-pass pointer return example:

    int *id(int *p) {
        return p;
    }

    int main(void) {
        int x;
        int *p;
        p = id(&x);
        *p = 11;
        return x;
    }

Must-fail examples:

    void x;
    *3;
    &3;
    int *p; int x; p = x;
    int *p; int x; x = p;
    void *p; *p;
    int *p; int *q; p < q;

Verification:

    make test

Exit criteria:

    All old tests pass.
    All new 0.0.1.3 tests pass.
    No warning output exists.

Status: done. accept_pointer_*.c and accept_void_ptr_roundtrip.c mirror the
must-pass examples; must-fail cases are covered by existing error_*.c tests.
Extra ty_*.c tests cover char/int param conversions, void * calls, double
deref, and incompatible pointer equality.

    11. Function calls with typed pointers
    12. Deviation notes and documentation
    13. Cleanup and invariants
    14. Final acceptance tests

Why this order:

    Types first gives sema a real source of truth.

    Lvalues before address/deref keeps assignment rules clean.

    Address before deref makes the first pointer runtime test simple.

    Function calls after basic pointer behavior avoids mixing too many failure
    modes at once.

    Notes are late because they should support real limitations, not drive the
    design.


Suggested First Implementation Stage
------------------------------------

I would begin with Stage 1 and Stage 2 together.

Reason:

    A Type module alone is harmless but not useful.

    Threading Type through declarations immediately proves the shape is right.

    It should preserve all existing behavior.

    If old tests break there, the type design is too invasive.

Do not start with parser pointer syntax.

Reason:

    Pointer syntax before typed symbols creates AST shapes that sema cannot
    reason about cleanly.

Do not start with codegen.

Reason:

    Codegen should consume semantic facts, not invent them.

Do not start with diagnostics.

Reason:

    We do not have warnings, and notes are only useful once there is a concrete
    limitation to explain.


Open Questions Before Coding
----------------------------

Question 1:

    Should char object declarations be accepted but runtime behavior considered
    limited, or should non-pointer char objects be rejected until byte-correct
    codegen exists?

Current leaning:

    Accept char as a type.
    Avoid tests that depend on byte truncation.
    Reject or note only if a construct would clearly miscompile.

Non-Goals Repeated
------------------

No arrays.

No pointer arithmetic.

No structs.

No unions.

No sizeof.

No casts.

No typedef.

No warning system.

No full C declarator grammar.

No K&R function definitions.

No claim that char runtime behavior is complete.


Definition of Done
------------------

0.0.1.3 is done when:

    - the compiler has a real Type model,
    - declarations use Type *,
    - expressions are typed by sema,
    - basic pointers are usable with & and *,
    - void * assignment compatibility works,
    - pointer equality and truthiness work,
    - function parameters and returns can use pointer types,
    - known deviations are documented,
    - no warning system is faked,
    - old tests pass,
    - new scoped tests pass.

The release is not done if:

    - pointer behavior is implemented through ad hoc codegen hacks,
    - function types are still only ret_void plus arity,
    - lvalue rules are scattered across parser/sema/codegen,
    - C89 deviations are undocumented,
    - char is presented as fully working when it is not,
    - warning text is emitted without a real warning system.
